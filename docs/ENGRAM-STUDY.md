# Engram → HMEM 适用性评估

> 评估日期：2026-10-04 · 对象论文：DeepSeek-AI《Conditional Memory via Scalable Lookup:
> A New Axis of Sparsity for Large Language Models》(arXiv:2601.07372, 2026-01)

## 一、Engram 是什么（一句话）

Transformer 缺"原生知识查找原语"，被迫用 Attention/FFN **计算**去模拟**检索**（如记住
"Princess of Wales"这种定型短语要烧掉好几层）。Engram = 现代化的 **N-gram 嵌入表**，
把静态知识**烤进参数**、推理时 **O(1) 确定性查表**，再与隐藏态**门控融合**。

核心组件：①分词器压缩（NFKC/小写归一，词表 -23%）②多头哈希 N-gram 检索
③上下文感知门控 αₜ（检索到的静态记忆与当前上下文冲突时压制）④Zipfian 分层存储
⑤与 MoE 的 **U 型稀疏性分配定律**（~20-25% 非激活参数给 Engram 最优）。

## 二、为什么"整体搬到 HMEM"不成立（层次错配）

| Engram 前提 | HMEM 现实 |
|---|---|
| 知识在**预训练**时烤进 embedding 表 | HMEM 是**外部服务**，无训练、无反向传播 |
| 与 MoE 分配**参数预算** | HMEM 没有 MoE，参数预算是训练期概念 |
| 检索结果与**隐藏态 hₜ** 门控融合 | HMEM 返回**文本**，不接模型内部隐藏态 |
| 把局部依赖卸载给查表、**释放 attention** | HMEM 不跑 attention，无"注意力容量"可释放 |

论文标题里的增益（BBH +5、NIAH 84→97、CMMLU +4）**全部发生在模型内部**，
是"模型变聪明了"，不是"检索库变好了"。**Engram 是模型架构，HMEM 是记忆数据库，
两者不在同一层**——这是评估的核心结论。

## 三、可迁移的思想（逐个实测/论证）

### ✅ ① 分词器压缩 / 文本归一化 —— 值得做（低风险）

Engram 归一化后词表 -23%。HMEM 实测（真实库，`content_jieba` 列）：

| 库 | 记忆数 | 内容被归一化改变 | 词表压缩 | 归一化合并的同形 token 组 |
|---|---|---|---|---|
| dev.db | 199 | 100% | 4781→4627 (**-3.2%**) | 146 例 |
| default.db | 2036 | 97.6% | 48110→47853 (**-0.5%**) | 238 例 |

合并实例：`（` vs `(`、`⑦` vs `7`、`：` vs `:`、`Math` vs `math`、`MCP` vs `mcp`。
**结论**：归一化真实有效，但收益**小**（0.5-3.2%，远低于 Engram 的 23%——因为
HMEM 的 jieba 分词已吃掉了大部分中文分词问题）。**价值在正确性**（全角/半角、
大小写不一致时 FTS 能命中），适合作为**低风险卫生改进**。

### ✅ ② 上下文感知门控（αₜ）—— 最有价值，已落地（2026-10-04）

Engram 的关键洞察：检索到的静态记忆**不能无脑用**，要用当前上下文**门控**，
冲突则压制（αₜ→0）。HMEM 现状：FTS + 向量 + HRR **加权求和**（`_compute_score`），
词面命中和语义命中等权叠加——**一条词面高度重合但语义跑题的旧记忆会刷高分**。

**已实现**：`gate = clamp(hrr_sim / tau, floor, 1)`，乘到「纯词面命中」候选的
关键词分贡献上（`retriever._compute_score` 与 rerank 后路径均覆盖）。语义通道
（HRR/向量）已认可的候选不受影响。HRR 是**本地 numpy 相位相似度**——无 API、
不计成本、任何环境可跑；为 FTS-only 候选补算 `hrr_similarity`（`get_hrr_vector`
+ `similarity`）。参数：`HMEM_GATE_ENABLED`（默认 true）、`HMEM_GATE_TAU`（0.1）、
`HMEM_GATE_FLOOR`（0.5，保证不清零）。无 HRR 信号时门控为恒等（安全，不误伤）。

**实测**（`tests/test_semantic_gate.py` 3 用例 + 带标注合成语料 A/B）：
- 单元：门控将「字面高、语义低」陷阱的分数压低 ≥0.05，真相关（sim≥tau）分数不变；
  无语义信号时恒等；floor 保证不清零。
- 合成语料（3 topic × 3 relevant + 2 陷阱 + 10 干扰）：MRR **0.833 → 1.000**，
  recall@3 不变（3/3），trap@3 持平或下降。tau∈{0.05,0.1,0.2} 结果一致。
- 真实库（dev）：`supervisor 部署` 查询下，门控把无关的「Triple Town 汉化」
  挤出 top-3，换上 supervisor 主题条目。

> 逐条前后对比与完整复现命令见 [`docs/SEMANTIC-GATE-EVAL.md`](SEMANTIC-GATE-EVAL.md)。

### 🔸 ③ N-gram 倒排索引（O(1) 短语查找）—— 可选，收益存疑

Engram 的"哈希 N-gram → 静态表"。HMEM 版：建 bi/tri-gram 倒排表，让重复长短语
（"K8s 部署手册"）秒命中、免向量+rerank。但 **jieba + FTS5 已覆盖大部分**，
除非实测证明 FTS 对短查询/长短语召回弱，否则**边际收益低**。

### ❌ ④ U 型稀疏性分配 / Zipfian 分层 —— 不适用

前者是训练期参数预算问题；后者在 2000 条规模下 SQLite 已够快。

## 四、建议（按性价比排序）

1. **做**：文本归一化（NFKC + 小写 + 全半角），作用于 `_tokenize` + 查询侧同样归一。
   低风险、可回滚（只影响新增/重建索引），修 FTS 大小写/全半角漏检。→ **已落地**（见①）
2. **做**：词面命中的语义门控（HRR，本地无 API）。→ **已落地**（见②），MRR 0.833→1.000。
3. **暂缓**：N-gram 倒排（先测 FTS 短查询召回，有痛点再上）。
4. **不做**：整体移植 Engram（层次错配）。

> 若真想在"模型层"用 Engram：那是**换基座/微调**的事（需 DSA 训过 Engram 的模型权重），
> 与自建外部记忆库（HMEM）是两个正交方向，不能互相替代。

## 五、TF-Engram（2026-07, arXiv:2607.07388）—— 补充评估

**TF-Engram = Train-Free Engram with SSD-Backed Memory**。它针对原版 Engram 的两个痛点
重设计：①记忆要**训练**（学习表/投影/门控，与骨干绑定）②哈希压缩导致**短语碰撞、语义失真**。

**关键定性**：TF-Engram 是 **train-free（免训练）**——记忆条目不参与训练，靠「语料短语挖掘 +
冻结 embedding 编码」离线构建。这句话很关键，但要看清**免训练的是"记忆构建"，不是"记忆注入"**：
注入端仍挂在 **LLM 隐藏态**上（`h'ₜ = hₜ + gₜ·W·e_φ`），需要 GPU、NVMe SSD、改模型 forward
（early-exit 头 + 门控残差注入 + GPU-DRAM-SSD 分层预取）。

**论文实测**：backbone = **Qwen3-0.6B**（不是 30.6B！），十项下游均分 **57.6 → 59.4**
（+1.8，超过同参数 LoRA 的 58.7）。GPU 常驻 10M 表需 24GB 显存；SSD-backed 100M 表降到 3.06GB。

| TF-Engram 机制 | HMEM 对应物 | 结论 |
|---|---|---|
| 短语语义记忆（免训练，embedding 编码） | FTS + 向量 + HRR 检索 | **已等价具备**（TF-Engram 是给"没记忆的模型"补记忆） |
| 门控残差注入到隐藏态 | —— | **不可迁移**（HMEM 是外部服务，不接隐藏态） |
| GPU-DRAM-SSD 分层存储 | SQLite + FTS5 原生 | 规模不适用（4000 条 vs 100M 条） |
| Early-exit 预测预取 | —— | 不适用（无自回归解码循环） |
| N-gram 精确短语匹配 | FTS5（jieba 分词） | **已覆盖** |

**结论**：TF-Engram 让"模型层 Engram"从**必须预训练**变成**免训练即可用**——这是一次
真正的范式转换，值得关注。但它改善的是**"一个没有记忆库的 LLM 的答题能力"**，而 HMEM
**本身就是一套外部记忆库**：TF-Engram 里那套"短语记忆构建"（挖掘+embedding/或 n-gram）正是
HMEM 已有的检索能力；它剩下的独有价值（隐藏态注入 + SSD 预取）全部绑定"本地跑 LLM + GPU"。

**对 HMEM 的净增量**：≈0。若 HMEM 未来要托管自己跑的小模型，TF-Engram 可作为
"给该模型注入长期记忆"的选项——但那是**另一套系统**（需 GPU + 背模块），不是当前外部记忆库的增量。
HMEM 侧已经落地的两项（①NFKC 归一化 ②HRR 语义门控）恰好就是 TF-Engram "train-free / 语义保真"
思路在检索层的等价物，方向一致，无需重复投入。
